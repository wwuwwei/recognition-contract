
## 20260928统一测试用例
定义 contract → 添加 shared golden fixture → Android 实现 → Windows 实现 → 两端跑同一 fixture → production JSON validation。

这是这段时间**最重要工程成果之一**。

现在面对的已经不只是“Android 和 Windows 两份代码怎么写得一样”，而是更一般的问题：

> **怎样让同一个识别协议，在不同语言、不同客户端、不同运行时中保持同一语义。**

这套思路以后加入 iOS/Swift 时几乎可以原样扩展：

```text
                    Canonical Recognition Contract
                              │
                    Shared Golden Fixtures
                              │
              ┌───────────────┼───────────────┐
              ↓               ↓               ↓
        Android/Kotlin   Windows/Python    iOS/Swift
              │               │               │
        Fixture Runner    Fixture Runner    Fixture Runner
              │               │               │
              └───────────────┼───────────────┘
                              ↓
                     Expected Semantics
```

这样你真正维护的就不再是“三套算法规范”，而是：

> **一个协议 + 一套测试向量 + 三个平台实现。**

### 我建议把新增 primitive 正式规定成 7 步

以后不要再采用“Android 先写好了，然后 Windows 照着 Android 代码翻译”的模式，而是：

**① Define Contract → ② Add Golden Fixtures → ③ Android → ④ Windows → ⑤ iOS → ⑥ Cross-platform Gate → ⑦ Production Validation**

其中最关键的是把 **contract 和 fixture 放到实现之前**。

例如准备新增：

```text
hand_near_hand
```

第一步不是打开 Kotlin，而是先定义：

```text
Primitive:
hand_near_hand

Inputs:
HAND

Temporal:
STATIC

Args:
hand
point_a
point_b
max_distance

Coordinate:
normalized landmarks

Selector:
canonical HandSelector

Distance:
2D Euclidean

Boundary:
distance <= max_distance

Missing input:
fail-closed

Invalid args:
fail-closed
```

然后先产生共享 fixture：

```text
same hand / below threshold       → false
two hands / below threshold       → true
distance == threshold             → true
distance > threshold              → false
missing right hand                → false
invalid point                     → false
BOTH semantics                    → ...
```

**这时候甚至一行 Android/Windows/iOS 实现都还没有。**

随后三端实现的任务变成：

> “让自己的 implementation 通过 canonical fixtures。”

这和“互相照着代码抄”在工程意义上完全不同。

---

### 这也正好解决你面试里非常好的一个问题

如果面试官问：

> 你 Android 和 Windows 都实现了手语识别，怎么保证两端行为一致？

以前比较普通的回答可能是：

> 我尽量复用了相同算法，然后分别写单元测试。

现在你的回答可以升级成：

> 我后来发现仅仅让 Windows 按 Android 实现并不能真正保证语义一致，因为 Kotlin 和 Python 两边会出现默认值、非法参数处理、hand selector、temporal history、阈值边界等细微差异。
>
> 所以后来我把识别层重新定义成 platform-independent semantic contract。每个 primitive 先定义输入、参数、坐标系、阈值、selector、missing-data 和 temporal semantics，再建立共享 golden fixtures。
>
> Android 和 Windows 不互相作为 oracle，而是分别实现同一个 canonical contract，并消费同一组 test vectors。只有两端都满足 expected semantics，production JSON 也通过 schema/registry validation，这个 primitive 才能进入 production。
>
> 所以后面即使增加 iOS，我不需要再人工对照 Android 代码重写一遍，只需要实现相同 contract，然后让 Swift runner 跑同一组 fixtures。

这已经不只是“我会写测试”。

它体现的是几个很重要的工程能力：

**协议设计、跨平台一致性、contract testing、regression engineering、single source of truth、可扩展架构。**

而且你有非常具体的实际案例可以继续讲。

比如 `point_motion` 的 `ANY`：

```text
Android:
left trajectory
right trajectory
分别计算

Windows 原实现:
frame 0 left
frame 1 right
frame 2 left
→ 被错误拼成一条 trajectory
```

普通 happy-path 测试很可能发现不了。

而 parity audit 最终让你明确了：

```text
ANY = OR(per-slot trajectories)
BOTH = AND(per-slot trajectories)
```

然后把它冻结成 fixture。

这就是一个很好的面试故事：

**发现问题 → 找到根因不是算法本身而是 semantic contract 不明确 → 建立标准 → 自动化防止回归。**

### 更重要的是：以后 iOS 不应该再经历这次 P2

这是我们现在做 harness 最大的意义。

这次 Windows 对齐 Android，需要：

```text
inventory
→ audit
→ divergence
→ repair
→ test
→ closure
```

一个 primitive 一个 primitive 查，非常耗时。

但 iOS 加入以后应该变成：

```text
                   Existing canonical contract
                            +
                   Existing golden fixtures
                            ↓
                     Swift implementation
                            ↓
                      Swift fixture runner
                            ↓
                 487/487 fixtures passed
                            ↓
                    iOS parity CLOSED
```

而不是：

> “拿 Android 和 iOS 两个仓库打开，然后一份文件一份文件比较。”

这才说明这轮审计真正完成了架构升级。

---

所以我甚至建议我们不要简单把下一阶段叫做“补测试”。

可以正式把它定义为一个项目级标准，例如：

# Cross-Platform Recognition Contract

里面规定：

```text
Primitive Lifecycle

DRAFT
  ↓
CONTRACT DEFINED
  ↓
GOLDEN FIXTURES DEFINED
  ↓
PLATFORM IMPLEMENTED
  ↓
PARITY VERIFIED
  ↓
PRODUCTION ENABLED
  ↓
CLOSED
```

以后一个 primitive 如果只有 Android implementation：

```text
hand_xxx
Android: PASS
Windows: NOT IMPLEMENTED
iOS: NOT IMPLEMENTED
```

那它就不能被标成：

```text
PRODUCTION ENABLED
```

除非你明确规定这个 capability 是 platform-specific。

这会让你一个人开发时也拥有类似团队项目里的**工程治理规则**。

而且我认为这对你尤其重要：一个人开发最容易出现的不是“不会实现功能”，而是**没有第二个人帮你守住边界**。Contract、schema、golden fixture、CI 实际上就是把原本需要 reviewer 反复检查的规则变成机器执行。

你这次 P2 已经帮我们找到了大量适合成为这些标准的真实案例。下一步做 Post-P2 Harness 时，我建议我们不仅让 Codex“整理测试”，而是最终产出一份正式的 **`CROSS_PLATFORM_RECOGNITION_STANDARD.md`**。以后 Android、Windows、iOS 和 `words_release` 都按它工作。

这份东西未来也非常适合作为你整理项目技术路线和面试材料时的核心章节：**“从双端语义漂移，到建立跨平台 Recognition Contract 与 Golden Test 标准。”**
